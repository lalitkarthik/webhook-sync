Researched 2026-09-30 by three agents reading the code of the seventeen repos cloned in `D:\second-brain\repo-study\webhook\`. It builds on `D:\second-brain\freelance-vault\research\demo-baselines\02-webhook-sync.md`. File paths are relative to `repo-study/webhook/`. Claims marked **(verified)** were reproduced on this machine.

Verdicts: **take** = copy or adapt the code (permissive licence only, keep the notice); **idea** = reimplement (always for AGPL, GPL, ELv2 or no licence); **dependency** = use the library as it is; **skip** = not useful, with the reason.

## Summary

1. **No repo does the whole job, and none supports SQLite queues.** hookline is the closest receiver, driftless the best queue and sweeper design, sync-engine the best Sheets writer. All three have bugs that matter.
2. **The dedupe key differs per source.** Stripe puts it in `body.id`, Razorpay in the `x-razorpay-event-id` header, Standard Webhooks in `webhook-id`. hookline reads `body["id"]` and so rejects every Razorpay event.
3. **Every verifier fails somewhere.** hookline and razorpay-python accept an empty secret (fail open). Stripe's `verify_header` skips the time check unless a tolerance is passed, and never rejects a future timestamp. Every library turns some malformed input into a 500 instead of a 400. Standard Webhooks verifies the *last* duplicate header while FastAPI reads the *first*.
4. **Leases need fencing.** driftless and procrastinate let a worker whose lease expired mark a job done that a second worker now owns. The fix is a claim token plus a heartbeat.
5. **Never call a provider inside a DB transaction.** driftless does, which on SQLite locks every other writer. Fetch first, then one short `BEGIN IMMEDIATE` write.
6. **Classify errors.** driftless retries everything alike, so a poison job takes ~1.7 h to dead-letter. Bad data goes straight to the dead-letter queue; only 429, 5xx and timeouts retry.
7. **"Retry all dead" can abort entirely** in driftless when a newer live job exists for the same object. Retries must go back through the normal enqueue.
8. **Sheets gets the ledger row, never the event.** Then ordering is settled once, in the ledger, and the sheet needs no version guard of its own.
9. **sync-engine's Sheets writer is the one to port, with changes.** A failed read must abort the flush (sync-engine proceeds and duplicates rows, or pastes over the header). Replace `pasteData`/TSV with typed or RAW values.
10. **gspread traps.** `update_cell` forces USER_ENTERED (formula injection; `+91…` phone numbers become numbers), no timeout by default, full-Drive scope by default, `BackOffHTTPClient` retries appends on 5xx (duplicates).
11. **Worth taking as is.** saq's full-jitter formula (MIT). Svix's retry schedule, ±20 % jitter and attempt-log shape (MIT). driftless's per-object tables, event-type map, fetch mode, backfill horizon check and `verify` design (Apache-2.0).
12. **Built by nobody, so we build it.** Razorpay mapping, per-sink pause (so a sink coming back up isn't hit by a retry storm), currency exponents (JPY has 0 decimals, KWD has 3), the 50,000-character cell limit, a single-flusher lock, rebuilding the sheet from the ledger, handling requests during shutdown, and test vs live events on one endpoint.

### Bugs to avoid

- **Failing open when the secret is unset.** hookline `hookline/app.py` L21 (`b""` key accepts an empty-key HMAC, verified 202). accept-a-payment `custom-payment-flow/server/python/server.py` L144-157 and `elements-with-checkout-sessions/server/python/server.py` L103-110 trust the body unverified. razorpay-python `razorpay/utility/utility.py` L59-78 accepts `secret=""` (verified).
- **Parsing before verifying.** accept-a-payment `custom-payment-flow/server/python/server.py` L142 (`json.loads(request.data)` runs first; junk gives 500).
- **`return e` in Flask.** accept-a-payment `custom-payment-flow/server/python/server.py` L151-152: a bad signature becomes a 500 and the sender retries forever.
- **Emoji `print` on Windows.** accept-a-payment `server.py` L161/L165: `UnicodeEncodeError` when stdout is redirected (cp1252). Use `logging` and set `PYTHONUTF8=1`.
- **Uncaught non-`SignatureError` exceptions become 500s.** stripe-python `stripe/_webhook.py` L144-145 (`UnicodeDecodeError`) and L181 (`TypeError` on a non-ASCII `v1`). standard-webhooks `standardwebhooks/webhooks.py` L63 (`UnicodeDecodeError`) and L76 (`ValueError` on a malformed signature list). razorpay-python `utility.py` L61-73 (`TypeError` on bytes body or `None` signature). hookline `security.py` L42 (`TypeError` on non-ASCII). webhook-guard-py `signature.py` L53 (same). **Wrap every verifier as `except (VerifyError, ValueError, TypeError, UnicodeError) → 400`.**
- **Replay window silently off.** stripe-python `_webhook.py` L137: `verify_header(..., tolerance=None)` default skips the window. Always pass `tolerance=300`.
- **Future timestamps unbounded.** stripe-python `_webhook.py` L189 is a past-only check.
- **NULL ids never dedupe.** hookline `store.py` L16: `event_id TEXT PRIMARY KEY` without `NOT NULL` (SQLite quirk). `{"id": null}` is accepted twice (verified).
- **Dedupe key not scoped by provider.** hookline `store.py` L16: the PK is `event_id` only.
- **Open write transaction after a duplicate.** hookline `store.py` L53-61: `IntegrityError` is caught without `rollback()`, so the write lock is held and other writers get `database is locked` (verified). Use `ON CONFLICT DO NOTHING` or roll back.
- **Parsed payload stored instead of raw bytes.** hookline `store.py` L56: you can't re-verify or byte-replay.
- **Blocking sqlite in `async def`.** hookline `app.py` L37 (and webhook-guard-py's inline handler at `receiver.py` L102).
- **`time.sleep` in the worker, no jitter, no lease, cumulative attempt count.** hookline `dispatcher.py` L37, L48.
- **Same-tick double claim.** webhook-guard-py `idempotency.py` L64-65 (`setdefault` + equality on the timestamp). Worse on Windows with Python ≤3.12.
- **Idempotency record stuck forever / error responses cached.** asgi-idempotency-header `middleware.py` L57-91, `backends/memory.py` L148-156.
- **Dedupe scoped by client IP, keeping only the last record.** fidem `middleware.py` L53-54 and `store.py` `forget_previous_automatic` L140-151.
- **No HTTP timeout and no 429 retry.** razorpay-python `client.py` L181-239.
- **Handler inline in the request path.** webhook-guard-py `receiver.py` L101-105, and every accept-a-payment handler.

### Edge cases these repos handle or miss

- **Empty body.** hookline: 422 after the signature passes (verified). webhook-guard-py: 400 ("not valid JSON"). stripe-python: verifies `""` then `JSONDecodeError` (a `ValueError`, not a `SignatureVerificationError`). standard-webhooks: verifies, then `json.loads("")` raises `JSONDecodeError`. razorpay: HMAC of `""`. **None returns a clean 400 uniformly.** Plan: a 0-length body gives 400 before the HMAC.
- **Huge body.** None limit it except fidem (8 MB cap, `_too_large` L218-227). Even fidem reads the whole body into memory when there's no `Content-Length` (chunked). uvicorn has no default body cap. Plan: reject `Content-Length > 1 MB` with 413, and cap the streamed read.
- **Wrong content-type.** Nobody checks it (hookline accepted `application/x-www-form-urlencoded` with a JSON body, verified), which is correct for signature purposes. accept-a-payment's `request.get_json()` returns `None` for a non-JSON type and then 500s. Plan: don't reject on content-type; log it.
- **Non-UTF-8 body.** hookline: 422 when a BOM makes `json.loads` pick UTF-16, **500** for invalid UTF-8 inside JSON (verified). stripe-python, standard-webhooks: `UnicodeDecodeError` gives 500 (verified). razorpay: the caller must decode. webhook-guard-py: `json.loads` raises `UnicodeDecodeError`, which isn't caught (only `JSONDecodeError` is), so 500. **None handles it.** Plan: decode strictly and treat a failure as 400.
- **Duplicate headers.** FastAPI `Header()` and Starlette `.get()` take the **first** value (hookline verified: bad-first gives 401, good-first gives 202). standard-webhooks `verify(body, request.headers)` takes the **last** (verified). If the app dedupes on `request.headers.get("webhook-id")` but the library verified the last `webhook-id`, a captured request with an extra `webhook-id: <new>` header prepended passes verification under a fresh dedupe key within the 5-minute window. **None rejects duplicate security headers.** Plan: 400 if `webhook-id`/`-timestamp`/`-signature`, `stripe-signature` or `x-razorpay-signature` appears more than once, and pass `dict(request.headers)` (first value).
- **Multiple v1 signatures (sender-side rotation).** stripe-python: yes, `any()` over all `v1` (verified). standard-webhooks: yes, loops over space-separated signatures (but a double space crashes it, verified). hookline, webhook-guard-py, razorpay: single signature only.
- **Receiver-side secret rotation (two secrets live).** None: every verifier takes one secret. Plan: try each configured secret and record which one matched.
- **Clock skew.** hookline and webhook-guard-py: ±300 s two-sided. standard-webhooks: ±5 min fixed. stripe-python: past-only, so a fast local clock rejects everything and a slow one is tolerated. razorpay: no timestamp. Plan: log the skew seconds on every accept, and alert above 60 s (Windows `w32time` drifts on laptops).
- **Timestamp in the future.** hookline and webhook-guard-py reject beyond tolerance. standard-webhooks rejects beyond 5 min. **stripe-python accepts any future value** (verified +1 year).
- **Test vs live events at one endpoint.** None check `livemode`. stripe-python exposes `Event.livemode` (`_event.py` L79). Separate secrets per mode mean a single-secret verifier rejects the other mode. Razorpay bodies carry no mode flag (the secret differs per mode). Plan: a per-provider expected mode; store `livemode`; quarantine mismatches with 200 plus a flag.
- **Unknown event types.** hookline stores anything. stripe-python builds any type. accept-a-payment ignores unknown types and returns 200 (correct). Plan: store everything, and route only known types to sinks (the rest go to `status='ignored'`).
- **Event id missing.** hookline: 422 for a missing key but **accepts `null` (twice)**. webhook-guard-py: 400 (falsy check). stripe-python doesn't check. standard-webhooks requires the `webhook-id` header. **Razorpay has no body id at all, so hookline and webhook-guard-py reject every Razorpay delivery.** Plan: a per-provider key extractor (Stripe `body.id`, Razorpay `x-razorpay-event-id`, Standard Webhooks `webhook-id`); a missing key gives 400.
- **Same object, two different events** (Stripe docs; e.g. `payment_intent.succeeded` + `charge.succeeded`, or two event objects for one change). None handle it. The Event docstring mentions multiple events per action. Plan: sink rows keyed by `data.object.id` (natural key) with an upsert, plus a version guard.
- **Out-of-order delivery.** None handle it. hookline drains by `received_at`. Plan: upsert guarded by the object's own `updated`/`created` or a status rank, sticky terminal states, or re-fetch the object from the API.
- **Concurrent duplicate deliveries racing the insert.** hookline: PK + `IntegrityError` is correct (one connection, so effectively serialised). webhook-guard-py: lock + `setdefault`, **but the same-tick bug lets both win**. fidem: PK (Tortoise) or `asyncio.Lock` (memory), and makes the second request wait up to 15 s. asgi-idempotency-header: in memory the check and add have no `await` between them (safe in one loop); Redis `SADD` is atomic. Plan: `INSERT … ON CONFLICT DO NOTHING RETURNING` in the same transaction as the job insert, plus a barrier test with 16 threads and separate connections.
- **Same event id, different body.** None detect it (hookline keeps the first silently, verified by its own test L35-41). fidem is the only one that fingerprints the body (422 on mismatch). Plan: store `sha256(raw_body)` and log or flag a mismatch, while still acking 200.
- **DB locked on SQLite.** hookline: default 5 s timeout, no `busy_timeout`, blocks the event loop, and **holds a write lock after every duplicate** (verified). Others have no DB. Plan: one writer connection, `PRAGMA busy_timeout`, `BEGIN IMMEDIATE` for claim transactions, run DB calls off the loop, and 503 (so the sender retries) if it's still locked.
- **Request arriving after shutdown has started.** None handle it (hookline has no lifespan and never closes the store). uvicorn stops accepting and drains in-flight requests. Because the ack comes only after the commit, a killed request just gets redelivered and deduped. Plan: a lifespan that stops the worker and closes the DB; return 503 once the shutting-down flag is set.
- **Signed but non-object JSON (list or scalar).** webhook-guard-py: 400 (`isinstance` check). hookline: 422 (`TypeError` caught). stripe-python: `AttributeError` gives 500 (verified). standard-webhooks returns the list as-is (verified).
- **Signature header with non-ASCII bytes.** Every `compare_digest`-on-`str` implementation raises `TypeError`, a 500 (hookline verified via latin-1 header bytes; stripe, webhook-guard-py, razorpay verified directly).
- **Retries after the dedupe window expires.** webhook-guard-py forgets after 24 h and asgi-idempotency-header expires after 24 h, but Stripe retries for 3 days. hookline keeps rows forever (correct). Plan: keep event ids for ≥30 days (the Stripe events-list horizon).
- **Windows specifics.** Python ≤3.12 `time.time()` resolution breaks webhook-guard-py's claim. cp1252 stdout breaks accept-a-payment's `print`. `core.autocrlf` and a text-mode `open()` without an encoding change fixture bytes (razorpay tests). Open SQLite files block temp-dir cleanup (hookline tests don't close the store). The `.venv/bin` paths in hookline's README. The webhook-guard-py Dockerfile is Linux-only. WAL is fine on local NTFS but not on network or synced folders. Nothing in these receivers needs `fork()`.

Key driftless SQL to port, verbatim (`internal/store/queries/jobs.sql`, Apache-2.0, © quyumkehinde/driftless):

```sql
-- name: EnqueueJob :one
-- Coalescing enqueue: at most one live job per (object_type, object_id).
-- A conflict bumps the existing job to the newest event instead of adding a
-- row; the bump only moves latest_event_* forward, never backward.
INSERT INTO driftless.jobs (kind, object_type, object_id, latest_event_id, latest_event_created, priority, max_attempts)
VALUES ($1, $2, $3, $4, $5, $6, $7)
ON CONFLICT (object_type, object_id) WHERE status IN ('pending','running')
DO UPDATE SET
  latest_event_id = CASE
    WHEN COALESCE(EXCLUDED.latest_event_created, '-infinity') > COALESCE(driftless.jobs.latest_event_created, '-infinity')
      OR (COALESCE(EXCLUDED.latest_event_created, '-infinity') = COALESCE(driftless.jobs.latest_event_created, '-infinity')
          AND COALESCE(EXCLUDED.latest_event_id, '') > COALESCE(driftless.jobs.latest_event_id, ''))
    THEN EXCLUDED.latest_event_id
    ELSE driftless.jobs.latest_event_id
  END,
  latest_event_created = GREATEST(driftless.jobs.latest_event_created, EXCLUDED.latest_event_created),
  updated_at = now()
RETURNING id, (xmax = 0) AS inserted;

-- name: ClaimJob :one
-- Atomic claim: the SKIP LOCKED subquery guarantees no two workers get the
-- same row. attempts counts started tries, so jobs that crash a worker are
-- bounded by max_attempts through the reaper as well as the failure path.
UPDATE driftless.jobs
SET status = 'running',
    claimed_until = now() + sqlc.arg(visibility_timeout)::interval,
    attempts = attempts + 1,
    updated_at = now()
WHERE id = (
  SELECT id FROM driftless.jobs
  WHERE status = 'pending' AND run_after <= now()
  ORDER BY priority, id
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
RETURNING *;

-- name: CompleteJob :one
-- If a newer event was coalesced onto the job while it ran, the work that
-- just finished may be stale: requeue instead of done. Newer follows the
-- same (created, id) order as the payload-mode guard, ties included.
UPDATE driftless.jobs
SET status = CASE
      WHEN COALESCE(latest_event_created, '-infinity'::timestamptz)
           > COALESCE(sqlc.narg(claimed_event_created)::timestamptz, '-infinity'::timestamptz)
        OR (COALESCE(latest_event_created, '-infinity'::timestamptz)
            = COALESCE(sqlc.narg(claimed_event_created)::timestamptz, '-infinity'::timestamptz)
            AND COALESCE(latest_event_id, '') > COALESCE(sqlc.narg(claimed_event_id)::text, ''))
      THEN 'pending'
      ELSE 'done'
    END,
    attempts = CASE
      WHEN COALESCE(latest_event_created, '-infinity'::timestamptz)
           > COALESCE(sqlc.narg(claimed_event_created)::timestamptz, '-infinity'::timestamptz)
        OR (COALESCE(latest_event_created, '-infinity'::timestamptz)
            = COALESCE(sqlc.narg(claimed_event_created)::timestamptz, '-infinity'::timestamptz)
            AND COALESCE(latest_event_id, '') > COALESCE(sqlc.narg(claimed_event_id)::text, ''))
      THEN 0
      ELSE attempts
    END,
    run_after = now(),
    claimed_until = NULL,
    updated_at = now()
WHERE id = $1 AND status = 'running'
RETURNING status;

-- name: FailJob :one
UPDATE driftless.jobs
SET status = CASE WHEN attempts >= max_attempts THEN 'dead' ELSE 'pending' END,
    run_after = now() + sqlc.arg(backoff)::interval,
    claimed_until = NULL,
    last_error = sqlc.arg(last_error),
    updated_at = now()
WHERE id = $1 AND status = 'running'
RETURNING status;

-- name: ReapExpiredJobs :many
-- Resurrect jobs whose worker died without completing or failing them;
-- rows that exhausted their budget dead-letter instead, and the returned
-- statuses let the caller report the two outcomes separately.
UPDATE driftless.jobs
SET status = CASE WHEN attempts >= max_attempts THEN 'dead' ELSE 'pending' END,
    claimed_until = NULL,
    last_error = COALESCE(last_error, 'worker crashed or lost its claim'),
    updated_at = now()
WHERE status = 'running' AND claimed_until < now()
RETURNING id, status;

-- name: RetryDeadJobs :execrows
UPDATE driftless.jobs
SET status = 'pending', attempts = 0, run_after = now(), last_error = NULL, updated_at = now()
WHERE status = 'dead';

-- name: RetryJob :execrows
UPDATE driftless.jobs
SET status = 'pending', attempts = 0, run_after = now(), last_error = NULL, updated_at = now()
WHERE id = $1 AND status = 'dead';
```

Porting notes (ours, not driftless's):
- **SQLite 3.35+** supports partial unique indexes, `ON CONFLICT (cols) WHERE … DO UPDATE` and `RETURNING`. Check `sqlite3.sqlite_version` at startup.
- Replace `(xmax = 0)`, which is Postgres-only, with a `RETURNING created_at = updated_at` style flag. Replace `GREATEST` with scalar `max()`, `'-infinity'` with `0` (store epoch-ms integers), and `now() + interval` with `:now_ms + :vt_ms`.
- Drop `FOR UPDATE SKIP LOCKED` on SQLite. The claim runs inside `BEGIN IMMEDIATE`, and SQLite serialises writers.
- Add `claim_token` to `ClaimJob`/`CompleteJob`/`FailJob` (see Leases).

### Bugs to avoid

1. **Unfenced lease** (driftless `CompleteJob`/`FailJob`, procrastinate `finish_job_v1`). Completion matches `id + status='running'`, not the claimer. Put a `claim_token` on the row at claim and require it on complete/fail/extend.
2. **Reaper with no backoff** (driftless `ReapExpiredJobs`). A job that crashes the process is resurrected with its old `run_after` and re-crashes at once. Set `run_after = now + backoff(attempts)`.
3. **Bulk DLQ retry hits the live-job unique index** (driftless `RetryDeadJobs`). One conflicting object aborts the whole `UPDATE`. Retry dead jobs through the coalescing enqueue, or supersede them.
4. **Network I/O inside a DB write transaction** (driftless `Apply`, verify `repair`). Fatal on SQLite ("database is locked") and a long-tx risk on PG.
5. **Shutdown uses the cancelled context to record the outcome** (driftless `worker.go` `process`). The job is stranded until the reaper and burns an attempt. Record with a fresh context.
6. **All errors retried alike** (driftless queue). Poison jobs take ≈1.7 h to reach the DLQ. Classify permanent errors.
7. **Infinite immediate retries by default** (procrastinate `retry=True` → `RetryStrategy()`: `max_attempts=None`, wait 0).
8. **Retry counter not reset on manual retry** (procrastinate `retry_job_v2` increments `attempts`). A DLQ retry gets one shot. Reset to 0 as driftless does, and log the trigger as `manual`.
9. **Jitter that collapses at the cap** (convoy `exponentialBackoff.go`) or is too narrow (driftless ±20 %). Use full or equal jitter after the cap too.
10. **`NOT IN` over a nullable column** (saq `_dequeue`). Ungrouped jobs starve. Use `NOT EXISTS`.
11. **Cached "I hold the session advisory lock" flag on a pooled connection** (saq `sweep`). If the pool recycles the connection, two leaders run. Use a transaction-scoped lock or a DB lease row per pass.
12. **Check-then-insert dedupe with a non-unique index**, and **an empty dedupe key treated as a real key** (convoy).
13. **Missing counters on secondary paths** (driftless: reaper dead-letters skip `jobs_dead_total`, so the alert misses them). Increment metrics wherever the status changes, ideally from the SQL `RETURNING`.
14. **Clamping the server's `Retry-After` down** (svix `limit_retry_delay`). Never retry sooner than a 429 asks (matters for Sheets' "wait about a minute").
15. **App clock vs provider clock for the sweep window** (driftless `window`). Keep overlap ≥ plausible skew, and on Windows sync time (w32time) or read Stripe's `Date` header.
16. **Only `last_error` kept, or no error persisted at all** (driftless / procrastinate). The DLQ page needs an attempts table.

**sync-engine Sheets writer, step by step (what to port):**

1. **Per record** (`index.ts` L760-857): strip `_row_key`/`_row_number`. Throw if `newer_than_field` is missing. Check enum validations. Add `_synced_at`. `ensureHeadersForRecord`: on first sight of a stream, read the header row by tab title. If the tab is empty, create it with PK columns first, then the record's keys. If the record has new keys, append them to the header row and rewrite it. Build the row positionally as `headers.map(stringify)`.
2. **Classify:** tombstone → delete buffer; explicit `_row_number` → update buffer; has key → append buffer with in-batch dedupe (keep the newer by version); no key → plain append.
3. **Hold** `source_state` messages. When input ends, run `flushAll` (heartbeat log every 20 s).
4. **Read once:** for streams with keyed appends or deletes, one `values.batchGet`, narrow (PK plus version columns from row 2) when possible, else the whole tab.
5. **Row map:** serialised key → row number.
6. **Upsert split:** a pending append whose key exists becomes an update of that row, unless the sheet's version cell is not strictly older, in which case it's dropped. What's left are real appends. `existingRowCount` = rows read (+1 for the header on a narrow read).
7. **Deletes:** cancel delete+append pairs for the same key. Fill deleted slots with pending appends first. Otherwise move tail rows into the holes and blank the tail (the rows get reordered).
8. **applyBatch phase 1**, in parallel: `spreadsheets.get(fields=sheets(properties(sheetId,gridProperties)))`. For streams with an unknown row count, read `'tab'!A:A`.
9. **Phase 2:** if needed rows or columns exceed the grid, add `appendDimension` (rows plus a 1000 buffer, columns exact). Sort updates by row number and group contiguous runs. One `pasteData` per run at column A, `type: PASTE_VALUES`, delimiter `\x1f`, rows joined by `\n`, and `\n \r \x1f` inside cells replaced with a space. One `pasteData` per stream for appends at row `existingRowCount+1`.
10. **Cap checks:** refuse if the payload's cells > 10M, or if current grid + appended cells, or the projected grid, > 10M.
11. **Phase 3:** one `spreadsheets.batchUpdate` with the expansions first, then all pastes, wrapped in `withRetry`.
12. **After success:** log `row_assignments` (key → row), clear the buffers, **then** emit the held state messages. On failure: emit `connection_status: failed` and drop the states.

**Port changes for Python + gspread** (our design, so verdict idea):
- The sheet is a projection of the ledger. The flusher writes the ledger's **current** `payments` row, not the event payload, so **the sheet needs no version guard** (drop step 6's stale check). Ordering is settled once, in the ledger.
- Replace `pasteData` with `updateCells` rows of typed `userEnteredValue` (`stringValue` for ids and text, `numberValue` for amounts), `fields: "userEnteredValue"`, or with `values` RAW. That means no TSV escaping, newlines kept, no formula parsing. Keep "`appendDimension` first" in the same atomic `batch_update`.
- Address tabs by `sheetId` stored in the DB. Read the header, key and version columns in one `values_batch_get` with `UNFORMATTED_VALUE` on every flush.
- Flush every 3-5 s or every N rows, not at end of input. Chunk each `batch_update` to ≲2 MB and a few thousand rows. Mark the ledger's sink jobs done only after the call returns.
- Any read failure aborts the flush (never "proceed without dedup"). A 429/5xx/timeout requeues the jobs with `run_after = now + min(cap, base·2^n) + jitter`, honouring `Retry-After`. Never sleep inside the flusher.
- Drop the delete/tail-swap logic. Payments are never removed from the sheet; they get a status.
- Hold one flusher lease (see edge cases).

### Bugs to avoid

1. **Proceeding when a read fails** (sync-engine `index.ts` L511-516 → duplicates; `writer.ts` L838-843 → appends pasted over row 1). A failed read of the key column must abort the flush.
2. **`values.append` for anything retried** (gspread `append_rows`, BackOffHTTPClient retries 5xx on it). Write at explicit coordinates so a replay overwrites the same cells.
3. **DB and sheet disagreeing on ties**: `>=` in `upsert.ts` L208 / SQLite L75, strict `>` in `isStrictlyNewer`. Guard only in the ledger; the sheet copies the ledger.
4. **Second-resolution versions** (`event.created`) as the only guard. Add `(created, event_id)` plus status rank, and re-fetch on doubt.
5. **Type-sensitive row keys** (`serializeRowKey` JSON). Normalise every key to `str` on both sides.
6. **Reading keys/versions FORMATTED** and copying formatted values back (`index.ts` L657). Use `UNFORMATTED_VALUE`, and never round-trip sheet values into writes.
7. **pasteData/TSV** for user text: newlines lost, parsing not documented. Use typed `updateCells` or RAW.
8. **USER_ENTERED anywhere near provider data** (gspread `update_cell`). Formula injection, phone numbers turned into numbers.
9. **Postgres multi-row upsert with duplicate keys** in one batch (`upsertMany`, no dedupe). Collapse by key first, keeping the newest.
10. **Forgetting volatile columns** in a no-op diff (`upsertMany` `_synced_at`), which turns every upsert into a write.
11. **Hard delete without a tombstone** (`deleteMany`), which resurrects rows. Soft-delete and keep the version.
12. **Dead config**: `batch_size` in the Sheets spec (never read) and `revalidate_objects` (needs `isFinalState`, which is never set). Test every option you expose.
13. **Retry loops shorter than the quota window** (`withRetry` 31 s) and blocking sleeps (BackOffHTTPClient). Requeue with jitter and honour `Retry-After`.
14. **No HTTP timeout** (gspread default `None`).
15. **Addressing tabs by title** for reads while writing by sheetId (sync-engine), so a rename splits the data. Resolve everything via the stored sheetId.
16. **`created > cursor` event polling with no overlap** (`src-events-api.ts`). Overlap by ≥60 s and dedupe by event id.
17. **Test fakes that don't model the API** (`memory-sheets.ts`: `appendDimension` no-op, pastes stored verbatim). Keep one integration test against a real test sheet for coercion, grid limits and 429s.
18. **Over-broad scopes** (gspread `DEFAULT_SCOPES` includes all of Drive).

### Edge cases these repos handle or miss

| Edge case | Who handles it, and how | Our answer |
|---|---|---|
| Someone edits, sorts or deletes rows | sync-engine: rebuilds the row map from the sheet on every flush, so a sort *between* flushes is fine; warning-only protection; Overview duplicate counter. A sort *during* a flush (between read and write) makes updates land on the wrong rows. A deleted row only comes back when that object changes again. gspread: none. driftless: n/a. | Same per-flush re-read + warning protection + a hidden `ledger_rev` column. Verify compares key sets and revs; any drift triggers a row repair or a full rebuild. Keep the read→write window short. |
| Someone inserts a column | sync-engine: headers cached per run, so a mid-run insert misaligns positional writes. Across runs the header is re-read, and the user's column gets **blanked** whenever that row is updated. | Read the header row in the same batchGet every flush. If it isn't exactly our expected header, stop writing and alert or rebuild. Never write positionally against an unverified header. |
| Tab renamed or deleted | sync-engine: writes by sheetId but reads by title, so a rename creates a new same-named tab (split data), and a deleted tab is recreated holding only new or changed rows. gspread: `WorksheetNotFound`. | Store the sheetId; resolve it each flush from one `spreadsheets.get`. Renamed: keep writing by sheetId. Deleted: create it and run a full rebuild from the ledger. |
| Sheet hits the 10M-cell limit | sync-engine: local pre-check throws, no rollover, stuck. Others: none. | ~16 fixed columns, grid trimmed to them (≈600k rows). Alert at 80%, then roll over to a new tab or spreadsheet per period. |
| Two processes flushing at once | none (sync-engine has no lock; driftless's advisory locks cover DB writes only). | One flusher lease in the ledger: `pg_try_advisory_lock` on Postgres; a `leases` row with owner + expiry taken under `BEGIN IMMEDIATE` on SQLite. |
| 429 in the middle of a flush | sync-engine: `spreadsheets.batchUpdate` is all-or-nothing, so nothing is half-written; `withRetry` resends the same request (same coordinates, safe) for up to 31 s, then fails the whole run. gspread BackOff: blocking sleeps. | Abort the flush; jobs stay pending with `run_after` + jitter. The next flush re-reads, so there's no stale row map after a long wait. |
| batchUpdate succeeded but the response was lost | sync-engine: fixed-coordinate paste makes a replay idempotent, but network errors (string codes) aren't retried; the run fails, state isn't emitted, and the next run re-reads and turns the appends into updates, so no duplicates. gspread `append_rows`: duplicate. | Treat as unknown: the next flush re-reads keys and `ledger_rev` before writing; jobs are marked done only after a verified read or a clean 200. |
| Key values that Sheets reformats (leading zeros, long ids → scientific notation, dates) | sync-engine: Stripe ids are prefixed strings, so safe by luck; the pasteData coercion risk is undocumented. gspread RAW keeps strings; USER_ENTERED doesn't. driftless: n/a (no sheet). | Key = `"{provider}:{id}"` written as `stringValue`; read back UNFORMATTED. Phone and receipt fields also go as strings. |
| Minor units, zero-decimal (JPY) and three-decimal currencies | none convert. sync-engine and driftless store raw integers (driftless as `bigint` + `currency`). | Keep `amount_minor`, plus a display amount via a currency-exponent table. Never use floats in the ledger. |
| Partial vs full refunds | sync-engine and driftless mirror refund objects and `amount_refunded`; no roll-up. | `refund_status` derived per provider (Stripe `amount_refunded` vs `amount_captured`; Razorpay `refund_status`); refund failures lower it again. |
| Payment state going backward | sync-engine: timestamp guard only, and ties are resolved differently in the DB and the sheet. driftless: fetch mode writes current truth; the payload mode guard is `(created, id)`. | Stripe: fetch mode. Razorpay: payload + `(created_at, status_rank)`, with a re-fetch on a tie. Allow-list legitimate reversals (refund failed, dispute won). |
| Object deleted upstream | sync-engine: hard delete, resurrection possible; sheet tail-swap. driftless: soft delete on `deleted:true`, 404 or a deletion stub. | Soft delete in the ledger; the row stays in the sheet with status `deleted`. PaymentIntents can't be deleted, so this mostly affects customers. |
| Timezone of timestamps | sync-engine: raw unix `created` in the sheet, `_synced_at` as UTC ISO, `_updated_at` timestamptz. driftless: `to_timestamp()` → timestamptz. | Ledger in UTC. Sheet gets ISO-8601 text with an explicit offset in a configured business timezone (e.g. `+05:30`). Don't let USER_ENTERED parse dates in the spreadsheet's locale and timezone. |
| Very long text fields (>50,000 chars per cell) | none. In sync-engine a long JSON cell fails the whole atomic batch with a non-retryable 400: a poison row, stuck forever. | Truncate to ~49,000 chars with a `…[truncated]` marker; the ledger keeps the full value. Isolate a failing row into the dead-letter queue instead of failing the batch. |
| Unicode / emoji | sync-engine and gspread send JSON over UTF-8: fine. None test it. | Python `str` is fine. On Windows, set `PYTHONUTF8=1` or give log handlers `encoding="utf-8"` so emoji in logs don't raise `UnicodeEncodeError` on a cp1252 console. |
| Newline or tab inside a value | sync-engine: `\n`, `\r`, `\x1f` replaced with a space (lossy); tab kept because the delimiter is `\x1f`. gspread: JSON values keep both. | `updateCells`/RAW keep them; no TSV, so nothing needs escaping. |
